# envmanifest v0.2 — Plan

**Status:** planning. Locked after v0.1 publish (see `docs/v0.1-publish-checklist.md`).

This document is the contract for v0.2. It exists because v0.1 was dogfooded against five real projects in this workspace and the dogfood produced a clear, ranked signal about which gaps actually block adoption versus which are theoretical.

---

## Context

v0.1.0 was test-driven across five projects on 2026-05-01:

| Project | Stack | Files | Resources drafted | What broke |
|---|---|---|---|---|
| `Ghost_Logic` (root) | Python + Rust + TS multi-component | 268 | 17 | Resources mashed across 7 components — root `.env` doesn't exist; each component has its own. 16 `dotenv.missing` errors, all spurious. |
| `Ghost_Logic/Inspector` | Python (FastAPI + Celery) | 5 | **0** | Scanner blind to Python. `.env` had 31 names + `.env.development` had 16; init produced an empty manifest, then check yelled `dotenv.undeclared` × 37. |
| `ProofOfAIWork` | Python (FastAPI) | **0** | **0** | Scanner saw no files at all (Python). `.env` had 17 real names — none drafted. First-run UX is "your contract is empty and your `.env` is full of undeclared things." |
| `maelstrom-runtime` | Python | 16 | 0 | Scanner saw 16 files, found 0 names. No `.env`. Empty manifest, clean check. Hard to tell from the output whether the project genuinely has no config or the scanner is simply blind. |
| `roast-this-startup` | Next.js on Cloudflare Workers | 93 | 8 | Worked correctly. Wrangler-binding parser flagged `ASSETS` as `binding.undeclared` — real signal. Regression baseline. |

The pattern is sharp: **JavaScript/TypeScript projects work; Python-primary projects produce empty or wrong manifests; multi-component repos get mashed.** Three of five projects in a workspace dominated by Python are functionally unusable on v0.1.

That's the v0.2 priority list, in order.

## Priorities

### 1. Python scanner — ship-blocker

Three of the five test projects are Python-primary. `os.environ.get()`, `os.environ[...]`, `os.getenv()` are the obvious patterns. But Python config is broader:

- **stdlib:** `os.environ["NAME"]`, `os.environ.get("NAME", default)`, `os.getenv("NAME")`
- **pydantic-settings (BaseSettings):**
  ```python
  class Settings(BaseSettings):
      database_url: str
      api_key: SecretStr
      class Config:
          env_prefix = "POAW_"
  ```
  Field names + `env_prefix` → resource names. `SecretStr` annotation → `kind: secret`.
- **dynaconf:** `settings.DATABASE_URL` references after `Dynaconf(...)` import. Harder; punt unless adoption demands.
- **django-environ:** `env('DATABASE_URL')`, `env.bool('DEBUG')`, `env.list('ALLOWED_HOSTS')`.

**Implementation strategy:**
- Use Python `ast` module via subprocess (Node calling Python) OR a JS Python parser. Subprocess is simpler and dogfood-friendly (Python is ubiquitous on dev machines).
- Confidence levels mirror existing JS scanner: `exact` for literal names, `template` for f-strings with literals, `dynamic` for variable index.
- Skip `__pycache__/`, `.venv/`, `venv/`, `.pytest_cache/`, `dist/`, `build/`, `*.egg-info/`.
- Skip test files: `test_*.py`, `*_test.py`, `tests/`, `conftest.py`.

**Done when:**
- ProofOfAIWork init produces ≥17 resources (matches `.env`).
- Inspector init produces ≥31 resources (matches `.env`).
- pydantic-settings BaseSettings classes are detected.

### 2. Dotenv fallback for `init`

When the scanner returns 0 references but `.env*` files exist, **fall back to drafting from dotenv names**. This is the single largest first-run UX bug v0.1 has — in three of five projects, `init` produced an empty manifest while a populated `.env.local` sat next to it.

**Heuristic:**
- Walk all `.env*` files. Collect distinct `SCREAMING_SNAKE_CASE` names.
- Apply the same name-classification heuristic the scanner uses (`*KEY|*TOKEN|*SECRET|*PASSWORD|*CREDENTIAL` → `kind: secret`; otherwise `kind: env`).
- Mark each drafted resource with the new `confidence` field (see below).

**Schema addition: `confidence` field on resources.**

Each resource gains an optional `confidence` field:

| Value | Meaning | Set by |
|---|---|---|
| `exact` | Found by the code scanner as a literal `process.env.NAME` / `os.environ["NAME"]` reference. | `init` when scanner found the name. Reconciles cleanly. |
| `inferred` | Drafted from `.env*` with no matching code reference. The contract assumes this name is real but cannot prove it. | `init` dotenv-fallback path. Distinguishable from `exact` and surfaceable by `doctor`/`check`. |
| `dynamic` | The scanner saw the name only via dynamic access (e.g. `process.env[varName]`). Resource exists for the contract, but origin is non-literal. | `init` when only dynamic refs were detected. |

**Why a field, not a comment:** comments don't survive YAML round-trips through formatters or programmatic edits, are invisible to the MCP layer, and lose the long-term signal. A field lets `envmanifest doctor` say "17 resources inferred but never confirmed by a code reference — run scan to validate." It also lets the MCP `explain_requirement` tool surface confidence to coding agents directly.

The field is optional and absent by default for backward compatibility with v0.1 manifests. v0.2's `init` always emits it; manual edits can omit it (treated as `exact` when consumed).

**Doctor surfaces confidence:**
```
$ envmanifest doctor
✓ manifest loaded
✓ 22 resources total
  ✓ 5 exact     (matched code refs)
  ? 17 inferred (drafted from .env, no code reference)
    → run 'envmanifest scan --explain' to see what code paths exist,
      or remove from manifest if the .env entry is stale
```

**Decision point resolved:** do it, do not prompt. Add a `--no-dotenv-fallback` flag for strict scanner-only behavior. First-run productivity > strictness.

**Done when:**
- Empty-scanner + populated-dotenv produces a non-empty draft manifest.
- Every drafted resource has a `confidence` field set.
- `doctor` summarizes counts by confidence.
- `inferred` resources are not double-penalized as drift errors — they're already weakly-grounded by definition.
- MCP `explain_requirement` exposes `confidence` to agents.

### 3. Multi-env file precedence

Inspector loaded both `.env` (31 names) and `.env.development` (16 names) for `env=local`. The union (47 names, ignoring overlap) inflated the `dotenv.undeclared` list and made the doctor output unreadable.

**Decision (matches the dotenv ecosystem standard):**

```
.env.{environment}.local  >  .env.local  >  .env.{environment}  >  .env
```

First match wins per name. Each name is attributed to exactly one source file in the doctor output.

**Done when:**
- `envmanifest doctor --env dev` prints which file each `.env` name came from.
- Two files declaring the same name → the higher-priority one wins, the lower one is silently shadowed (or warned about under `--strict`).
- Documented in the spec (`docs/spec-v0.md`) and the schema description.

### 4. Multi-component repo handling — `workspace.yml`

`Ghost_Logic` is a single git repo containing seven distinct projects: Agent_Rust, Blackbox, Inspector, Arbitrator, blackbox-console, blackbox-agent, Ghostlogicforensicapp. v0.1's root `init` mashed all 17 detected names into one manifest reconciled against a non-existent root `.env`. Wrong shape.

**Detection:** at `init` time, before scanning, check for these in subdirectories:

- `package.json` (Node project)
- `pyproject.toml` / `setup.py` (Python project)
- `Cargo.toml` (Rust project)
- `wrangler.toml` / `wrangler.jsonc` (Cloudflare Worker)
- `go.mod` (Go project)

If two or more subdirectories at depth ≤2 contain any of the above, the repo is multi-component. **Refuse to mash. Offer:**

```
$ envmanifest init
Detected 7 component projects:
  apps/api          (pyproject.toml)
  apps/web          (package.json)
  apps/agent        (Cargo.toml)
  ...

Run 'envmanifest init' inside each component, or generate a workspace.yml
that points at all of them?

  1) Generate workspace.yml + per-component manifests
  2) Mash everything into one manifest.yml at this root (NOT recommended)
  3) Cancel

>
```

**`workspace.yml` minimum schema for v0.2:**

```yaml
version: 0
project: ghost-logic
manifests:
  - path: Agent_Rust/manifest.yml
    component: agent
  - path: Blackbox/manifest.yml
    component: blackbox
  - path: Inspector/manifest.yml
    component: inspector
  # ...
```

Aggregation operations defer to v0.3. The minimum v0.2 wedge is "stop mashing, point at the right per-component manifests." Fleet-level reporting is paid Team-tier territory.

**Non-interactive / CI behavior — explicit decision:**

When `init` runs in non-interactive mode (detected via `--non-interactive`, `--ci`, `CI=true` env var, or non-TTY stdin) and detects a multi-component repo, it **refuses and exits non-zero** with a printed instruction:

```
$ envmanifest init --ci
✗ multi-component repository detected (7 component projects found below this directory)

  Cannot mash a multi-component repo into a single manifest.yml safely
  in non-interactive mode. Choose:

    1. Run 'envmanifest init' inside each component directory, or
    2. Run 'envmanifest init --workspace' to generate workspace.yml
       pointing at per-component manifests.

  See https://env.ghostlogic.tech/docs/workspaces for details.

[exit 2]
```

Never silently mash in CI. Never auto-pick `--workspace` either — that's a workflow shape decision the user has to make. Exit code 2 distinguishes "configuration shape problem" from exit 1 (drift / contract violation), so downstream CI can branch on it.

Interactive mode (TTY stdin) gets the same prompt as the v0.1 default behavior, with a third option that defers the decision: cancel without writing.

**Done when:**
- Multi-component detection works on Ghost_Logic, on common monorepo patterns (turbo, nx, pnpm workspaces), and on Cloudflare Pages projects.
- `envmanifest check --workspace` reads `workspace.yml`, runs check on each pointed-at manifest, returns aggregated exit status.
- CI invocation refuses to mash, exits 2 with actionable instructions.

## Deferred

The following are **explicitly not in v0.2**:

- **`kind: service`.** No dogfood demand from this pass. Five projects, zero needed cross-component contract declarations beyond what `kind: env, type: url` + `kind: secret` already cover. Revisit in v0.3 if Team-tier customers ask for it.
- **Go scanner.** No Go projects in the dogfood set that need it. (Agent_Rust is Rust, not Go.)
- **Rust scanner.** Same — Rust uses `std::env::var` which is detectable, but `Agent_Rust` was the only Rust project in the dogfood and no one tried to dogfood envmanifest against it.
- **Seal level L4 (runtime probes).** Phase 2 paid feature. Not v0.2.
- **Cloud adapters.** Phase 2 paid feature.
- **Vercel binding parser.** No projects in the dogfood deploy to Vercel. Wrangler covers Cloudflare; we already see that working.
- **Schema v1 lock.** Stays at v0 experimental until at least 6 months or 100 active users (per spec).

## Launch-Blocker Statement

**Python scanner + dotenv fallback are the minimum bar for public npm launch.**

If v0.1 ships to npm with these gaps unresolved, the first wave of "I tried it on my Python project" issues will dominate the bug tracker and the wedge ("config contract layer for AI-assisted software delivery") will read as "JavaScript-only env validator with extra steps." The MCP and seal stories don't compensate.

The publish-checklist (`docs/v0.1-publish-checklist.md`) acknowledges this honestly with a README scope statement and a "known gaps" release note. Publishing v0.1 with documented gaps is correct — it gets external bug reports flowing — but **the v0.2 timeline is the credibility timeline**. If v0.2 takes more than 2 weeks after v0.1 launch, momentum dies.

Multi-component / `workspace.yml` is desirable but not a launch blocker — single-project users (the larger market) aren't blocked by it. Defer if v0.2 timeline gets tight.

### Telemetry / Feedback channel

The v0.2 priorities are derived from **five projects in one author's workspace**. That's a sample, not a population. Once v0.1 is on npm, real adopters will hit gaps the dogfood didn't surface. We need a low-friction way to learn what they hit without violating the privacy posture (the whole product is "names + metadata only, never values" — feedback can't betray that).

**Spec for v0.2 (or v0.1.1, see Timeline):** an `envmanifest feedback` command:

- Pre-fills a GitHub issue template with **anonymized** scan stats:
  - file count scanned, by extension
  - resource count, by `kind` and `confidence`
  - whether `.env*` files were present and how many distinct names they had
  - whether the scanner returned 0 (the "Python or other unsupported language" signal)
  - whether multi-component detection fired
  - envmanifest version, OS, node version
- **Never includes**: resource names, file paths, project name, env values, machine identifiers.
- **Opt-in only.** The command never runs automatically; it never auto-sends. It opens a browser to a pre-filled GitHub issue URL the user must explicitly submit.
- Output text format the user reviews before submitting:
  ```
  envmanifest feedback — preparing report
  
  Scanner: 268 files (.ts:120 .js:14 .py:134), 0 names found
  Dotenv: 3 files, 47 distinct names
  Multi-component: detected (7 children)
  Environment: envmanifest 0.1.0, win32, node v20.11.0
  
  This will open GitHub in your browser with the above information
  pre-filled. No names, paths, or values are included.
  
  Submit? [y/N]
  ```

This is how v0.2 priorities get **re-validated against real adoption** rather than confirmed against five projects. If the inbox shows 80% Python projects, Priority 1 is correct. If it shows 80% TS projects with deep monorepos, Priority 4 jumps to the front.

The feedback infrastructure is itself low-cost: a pre-filled GitHub URL, no backend, no telemetry server. Costs ~50 lines of code.

## Timeline

**Target: 2 weeks from v0.1 npm publish to v0.2 npm publish.** The credibility window is real — published-with-known-gaps reads as "intentional staged release" for two weeks, and as "abandoned project" past that.

| Week | Work | Ship-target |
|---|---|---|
| Week 1 | Python scanner + dotenv fallback (with `confidence` field) | The launch-blocker pair. v0.1.1 if needed. |
| Week 2 | Multi-env file precedence + multi-component detection + `workspace.yml` | v0.2.0 proper. |

**Slip plan.** If Week 1 takes longer (likely — Python AST + pydantic-settings is more work than the JS scanner was):

- Ship `v0.1.1` at the end of Week 1 with **only** Python scanner + dotenv fallback. That alone moves three of five test projects from "broken" to "works."
- Defer precedence rules and `workspace.yml` to `v0.2.0`, which can take Week 2 plus a buffer week if needed.

**Hard cap.** If we hit week 4 with no v0.2-anything published, stop adding scope and ship whatever's stable as v0.2.0, even if it's only Python. Momentum > completeness past that point.

The `envmanifest feedback` command should ship in the **first** v0.2.x release (whether that's `v0.1.1` or `v0.2.0`). Adoption signal compounds — every week without it is a week of decisions made on the original 5-project sample.

## Open Questions

1. **Precedence edge cases.** What if a name appears in `.env.production` but the active env is `dev`? Currently it's silently filtered out at scope time. Should `doctor` mention "you have a name declared for production that's not declared for dev — possible drift"? Probably yes; defer to v0.3.

2. **`workspace.yml` schema design.** Does it have its own `policies` block that components inherit? Does it have global `ignore` patterns that components inherit? Or is it strictly a pointer file? My current take: strictly a pointer file in v0.2; inheritance comes in v0.3 once we see how people actually use it.

3. **pydantic-settings env prefix collision.** If two BaseSettings classes use different `env_prefix` values, names can collide (e.g., `POAW_DATABASE_URL` vs `INSPECTOR_DATABASE_URL`). Each is a distinct resource; that should fall out of the scanner emitting fully-prefixed names. Worth noting in tests.

4. **What if `init` is run twice?** Currently the existing `manifest.yml` blocks without `--force`. With dotenv-fallback, "no scanner refs but dotenv has names" might suggest a merge mode rather than an overwrite. Not a v0.2 blocker; mention in v0.2 docs as "future work."
